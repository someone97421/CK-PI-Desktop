# 主 Agent 与子 Agent 协作实现方案

- 编写日期：2026-09-17。
- 实施分支：`agent-combo`，从 `main` 的 `81ee7ebc` 创建。
- 状态：代码实现已完成；构建、定向测试及验证边界见第 12 节。
- 产品依据：[协作决策](./SUBAGENT-COLLABORATION-DECISIONS.md)。出现语义冲突时，以该文档的用户确认行为为准。
- 实施原则：在用户指定的 `agent-combo` 分支工作。本轮用户明确要求代码构建和最轻量的基本连通性测试，已按相关路径执行，结果见第 12 节。

## 1. 方案概览

子 Agent 持续执行，运行时旁路收集工具事件，每 N 个完成步骤生成增量报告。报告由父运行时调度进入主 Agent 上下文，不通过子 Agent 的模型请求生成或传递。

主 Agent 用 `TaskGuide` 提交引导。子运行时从接收命令起拦截后续工具，等待当前工具结果收束，在原上下文中应用引导、重置本段计数并自动继续。用户按钮与 `TaskStop` 走同一个定向终止控制器。

```text
子 Agent 工具执行事件
  ├─ 原有界面/转录记录
  └─ 步骤记录器 → 每 N 步截取快照 → 后台摘要 → 主 Agent 报告队列
                                                  ↓
主 Agent 独立执行 ← 可处理边界交付报告 ← 状态、摘要、记录引用
  ├─ TaskGuide → 子任务控制器 → 当前工具结束 → 应用引导 → 自动继续
  └─ TaskStop  → 子任务控制器 → 禁止新动作并取消在途工作
用户终止按钮 ────────────────┘
```

## 3. 设置与生效规则

增加可选字段 `reportIntervalSteps?: number`。

1. 设置界面显示“汇报间隔（工具调用次数）”，留空提示“由主 Agent 派发时指定”。不设置虚构的统一默认 N。
2. 用户定义固定值优先；没有固定值时使用 `Task.reportIntervalSteps`。两者均缺失则返回参数错误，启动前失败。
3. 仅接受正安全整数，拒绝隐式字符串转数值、负数、小数和把 `0` 当成关闭。
4. 派发时保存生效值与来源快照；编辑设置默认影响后续派发，不悄悄改变已经运行的子任务。
5. 引导可以携带新间隔。若用户未固定，则引导生效时更新；省略则继承。若用户固定，则不同值返回明确冲突，而不是静默忽略。
6. 在可用子 Agent 目录、`Task` 描述和启动结果中声明间隔及来源。该设置控制程序旁路汇报，不要求子 Agent 自己执行计数或汇报指令。

内置子 Agent 现有界面仅支持开关和复制。第一版复用“复制为我的子 Agent”配置固定间隔；未复制的内置定义由主 Agent 在派发时指定。这样不需要为了本功能改写内置开关文件的结构。若后续要求直接编辑内置定义的间隔，另做独立可选覆盖配置，先说明兼容影响。

## 4. 运行记录与事件模型

以下是建议的内部结构，字段名可调整，标识和状态语义应保持。

| 结构 | 核心字段 |
| --- | --- |
| 运行控制记录 | `sessionId`、父轮次/代次、`delegationId`、运行句柄、运行状态、终止原因、待处理引导 |
| 计数记录 | `segmentId`、`reportIntervalSteps`、累计已发起/已完成步数、本段已完成步数、距上次截取报告的步数 |
| 步骤记录 | `toolCallId`、全局步骤序号、所属段、工具名、脱敏参数、开始/结束时间、结果状态、输出引用 |
| 阶段报告 | `reportId`、单调 `reportSeq`、段编号、步骤区间、截取时间、生成时间、原因、摘要、工具索引、截断信息 |
| 引导记录 | `commandId`、目标运行、引导文本、新间隔、接收时间、生效时间、状态、失败/取消原因 |

引导状态建议为 `accepted`、`applying`、`applied`、`cancelled`、`rejected`；运行状态区分运行中、等待引导生效、正在终止和最终状态。不要把短暂的工具边界让出处理成任务失败或需要人工恢复的长期暂停。

累计使用量只在原有路径记账，阶段报告不再次累加费用。队列有界；完整工具输出优先引用现有转录，避免长期复制两套大对象。

## 5. 自动汇报管线

### 5.1 记录与触发

在实际工具执行入口登记步骤，而不是把所有模型提议的 tool call 都视为已经执行。正常结束、执行错误及已发起请求的拒绝结果均收束一次；控制器提前拦下的旧计划不消耗步骤。

在工具结果确定后更新本段计数，满足 N 就冻结一份不可变快照，推进批次游标并把生成工作放入后台队列。不要在工具完成钩子中 `await` 主 Agent 审阅或后台摘要模型。

子任务完成、终止或引导切换执行段时，截取不足 N 的剩余记录并标明原因。最终结果和最后一份阶段报告通过记录引用去重，不重复发送整个过程。

### 5.2 第一版摘要

第一版使用程序生成的结构化摘要：工具动作、可核实的成功/失败、结果短摘录、最近可见的 Agent 陈述和文件引用。事实记录优先，不额外启用摘要模型或增加模型选择设置。

如后续加入语义摘要器，应在快照上异步运行，并具有失败降级：异常时发送结构化记录，不能阻塞子任务或无限积压。独立模型摘要的选择、额度和成本需单独明确。

不向主 Agent 转发原始凭据或不必要的私人数据；沿用并补足已有脱敏规则。工具输出是待分析数据，不因进入报告就升级成系统指令。保留完整记录的权限边界。

### 5.3 主 Agent 交付

父运行时维护报告收件箱，以 `(delegationId, reportSeq)` 去重，并记录是否进入父模型上下文。

- 父 Agent 正在生成回复：排队，在当前请求之后的可处理边界交付，不并发启动同一 Agent 的第二个 prompt。
- 父 Agent 正在执行工具：不粗暴中止其工具，在下一可处理边界合并交付。
- 父 Agent 正在 `TaskWait`：阶段报告可唤醒等待，返回“仍在运行”和本批增量，不能伪装成已完成。
- 父 Agent 已进入等待子任务收束的空闲恢复路径：报告可以唤醒该路径，而非继续等待所有子任务结束。
- 会话已被用户停止、父轮次已替换或运行已释放：禁止旧报告重新启动已结束的父轮次。

多个子任务同期报告合并成一批父上下文消息，优先交付终止/失败等状态。合并不能丢失报告区间，可保留简明最新状态和各报告引用。父模型响应或最终报告本身不触发工具步数汇报，避免形成消息循环。

`TaskWait` 获取报告和自动投递共用交付游标，不能把同一份报告重复注入。报告尚在摘要队列中时不得阻塞子任务完成；终态和确定的工具记录可以先到达，后来的摘要仍须带原报告标识。

## 6. 引导控制与工具边界

### 6.1 `TaskGuide`

```ts
type TaskGuideInput = {
  delegationId: string;
  instruction: string;
  reportIntervalSteps?: number;
};

type GuideReceipt = {
  delegationId: string;
  commandId: string;
  status: "accepted" | "applying" | "applied" | "cancelled" | "rejected";
  reason?: string;
};
```

`sessionId` 和父运行归属由运行时绑定，不能让模型任意指定其他会话。工具快速返回接收回执，不等待可能耗时很长的当前工具结束；后续生效状态通过报告/控制事件和 `TaskList` 查询可见。IPC 重试使用同一命令 ID，避免重复插入或重复重置计数。

### 6.2 执行顺序

1. 校验目标属于当前会话且仍可引导，校验文本和间隔，分配命令 ID。
2. 在任何异步等待前登记命令并关闭旧计划的工具执行入口。
3. 已开始的工具继续，结果归入旧执行段；尚未开始的工具不再实际执行。
4. 收束旧模型回复中未执行的工具调用，保持消息协议合法，记录为“因引导未执行”，不得伪造成功结果。
5. 在调用链安全边界，把引导插入同一个子 Agent 的消息上下文；不使用整个运行的 abort 来模拟可继续暂停。
6. 刷新段编号，截取旧段尾部记录，更新允许更新的间隔，重置本段与批次计数。
7. 发布 `applied` 回执，开放新计划的工具入口，使用同一上下文自动继续。

如果当前是模型生成阶段，先锁住后续工具，待回复收束后处理其中的旧计划并应用引导。引导不承诺打断一个正在生成的 token；真正需要立即取消时使用终止。若子任务已正常完成而引导尚未接收，返回终态，不自动重启。

多个引导按接收顺序登记；同一边界之前到达的引导可以按顺序组成一次输入，仍分别回执。不能悄悄丢弃已接受的命令。相互冲突时保留顺序及来源，最新有效要求在用户目标和权限边界内解释；不能用引导提升权限。

### 6.3 底层适配重点

当前子 Agent 顺序执行工具，适合设置入口闸门。但仅调用 `agent.steer()` 或仅在 `afterToolCall` 返回终止提示，均不足以保证 A 完成后不执行 B、C。

实现使用执行前拦截关闭旧计划入口，以 `shouldStopAfterTurn` 让出循环，再通过同一实例的 `prompt()` 追加引导并继续。拦截结果使用 `SUBAGENT_GUIDED` 或 `SUBAGENT_STOPPED` 控制原因，保留合法的工具结果配对；只有实际执行过的工具才进入步骤计数。

若现有钩子无法正确表达该边界，应新增局部执行适配器或受控依赖补丁，并说明影响；禁止直接编辑 `node_modules` 后把本机效果视为仓库实现。

## 7. 查询工具与主 Agent 指令

保留 `Task`、`TaskWait`、`TaskList`、`TaskStop` 的既有职责，按兼容方式增加阶段报告和控制状态。

- `Task`：增加可选间隔参数，条件必填校验在运行时执行；结果包含生效间隔和来源。
- `TaskList`：展示运行状态、累计次数、当前段、最近报告及引导回执。
- `TaskWait`：支持报告到达唤醒；结果明确区分阶段进展与任务完成，保留原有终态信息。
- `TaskGuide`：仅用于中途引导，不兼任终止或创建任务。
- `TaskInspect`：按子任务 ID 和步骤范围获取有界详细记录，并支持按 `toolCallId` 或历史页查询持久化转录，避免扩大每份自动报告。
- `TaskStop`：和人工停止共用控制器，不能因等待无法取消的工具而无限阻塞主 Agent。

更新父 Agent 的派发说明，移除“运行中不能纠正子 Agent”的旧表述，说明汇报持续并行、引导回执与人工终止的含义。把新增控制/查询工具加入子 Agent 工具继承排除表，保持不嵌套派发、不越权控制其他子任务的边界。

## 8. 人工终止和优先级

增加定向请求，概念参数为 `{ sessionId, delegationId }`，经 Renderer → Electron IPC → Sidecar → 所属运行实例处理。路由名称实施时按既有命名统一。

停止控制器应在首个 `await` 前锁定停止意图、禁止新工具并取消待处理引导，然后传播模型与工具取消信号。Bash 已有 `tools.abort` 可复用；插件、MCP 等工具需分别核实取消支持。不得通过杀死共用 Sidecar 来停止一个子任务。

停止请求快速确认“正在终止”；确实收束后才发布终态。不支持即时取消的操作保留在途状态和说明，不提前把未完成的副作用包装成“已取消”。重试停止应幂等。

竞争处理优先级：用户整轮停止/会话销毁 → 单个子任务终止 → 引导 → 普通阶段报告。已经确认的终态不可被迟到的成功事件或引导回执改写。

人工终止事件明确标记来源并进入主 Agent 上下文，指示不要自动重建相同意图的工作。运行时禁止通过旧引导/重复控制复活同一个运行；不能宣称仅凭任务 ID 就能自动识别所有语义相同的新派发。

## 9. 界面和兼容性

设置页显示间隔输入、留空含义与现有输出上限的区别。运行卡片及详情页提供独立终止按钮；点击后禁用重复提交并显示“正在终止”。同时展示间隔、本段进度、累计步骤、最近报告和引导接收/生效状态。

只维护简体中文与英文。适配现有转录与拓扑布局，避免把子任务终止映射成主会话结束。

持久化在现有子 Agent Markdown 前置字段增加可选值，同步 TypeScript/Rust 读写和配置导入导出路径。旧文档缺字段可正常加载；新版本更新定义时保留其他前置字段。输入缺省表示保留间隔，显式 `null` 表示清除固定间隔。

兼容性有方向：新版本读取旧定义和旧导出文件；旧版本编辑并保存定义时可能丢弃新增间隔字段，旧版严格校验的配置导入器也不识别包含该字段的新导出文件。未设置固定间隔时导出省略此字段。本轮未修改数据库 schema、protocol 数字或凭据格式。

本方案不需要预先升级数据库 schema 或 protocol 数字。新字段、IPC 与事件按现有能力边界增量接入；若实现中发现必须改变不兼容格式或公共契约，先集中说明并确认。历史转录缺少新字段时正常展示。

第一版不承诺跨进程重启恢复运行中的子 Agent。仍要保留已落盘的报告、引导及终止记录，重启后不能把历史状态当成仍有活跃执行器。

## 10. 实施顺序与完成条件

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 一：控制基础 | 保存运行句柄、统一定向终止、接通人工按钮、处理状态竞争 | 可以只停止一个子任务，其他运行不受影响；停止状态真实且可追踪 |
| 二：汇报闭环 | 设置字段、派发生效规则、步骤记录、后台摘要、父收件箱、等待唤醒 | 到 N 自动投递增量，子 Agent 不等待；主 Agent 实际能读取报告且不会重复消费 |
| 三：引导闭环 | `TaskGuide`、工具入口拦截、消息配对、分段重置、原上下文继续 | A 执行时收到引导，A 后旧 B/C 不执行，指令生效并自动继续 |
| 四：收尾适配 | 查询详情、导入导出、历史兼容、双语文案、终态与异常收束 | 设置和运行状态一致，无报告丢失、子任务复活或父轮次错误结束 |

不把仅有 UI、仅能发报告或仅能排队 steering 视为整个功能完成。阶段实现状态应与已确认行为逐项对应，不预设人天承诺。

## 11. 定向验证场景

以下为实现核对清单。已执行的代码级覆盖及未进行的真实环境验证见第 12 节。

1. 固定 N、由主 Agent 指定 N、双方缺失、非法值，以及用户配置不能被引导覆盖。
2. 连续执行超过两个汇报周期：子 Agent 未等待主 Agent，步骤区间无重叠丢失，累计计数不重置。
3. 工具失败、重复事件、流式输出、未执行旧计划与不足 N 的尾部记录计数正确。
4. 主 Agent 正在生成、执行工具、`TaskWait`、空闲回收时均可收到阶段报告；不并发调用同一 Agent 的 prompt。
5. 一次回复含 A/B/C，引导在 A 执行期间到达：A 结果保留，B/C 不执行，消息协议完整，新指令之后自动继续。
6. 引导在模型生成、工具结束临界点和任务完成时到达；重复引导、多条引导和间隔更新无重复生效。
7. 人工终止只影响选中任务；终止优先于引导；等待审批和长命令能正确取消或如实显示未收束状态。
8. 报告延迟、摘要失败、多子任务同时汇报、父轮次替换和会话停止不会导致旧消息唤醒或重复执行。
9. `maxTokens` 仍是单次响应上限；达到 N 不停止任务；引导不重置累计用量。
10. 旧定义、历史转录、内置复制、导入导出和简中/英文界面兼容。

实施验证优先覆盖修改及相关路径，遵守项目默认不跑测试/全量构建的约定；需要执行时集中说明范围，并如实记录实际结果。

| 界面与历史 | 简中/英文显示间隔来源、本段和累计计数、最近报告、引导回执及停止来源；历史无活跃执行器的卡片不提供停止按钮 |
